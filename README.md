# ПРОБВАЙ

Виртуална проба на дрехи. Качваш своя снимка и снимка на дреха — или само
линк от магазина — и виждаш как ти стои, преди да поръчаш.

---

## Какво ти трябва

| | |
|---|---|
| Node.js | 22 или по-нов |
| Docker | за локалната база |
| PostgreSQL | 16 (идва с Docker) |

---

## Локално стартиране

```bash
# 1. Зависимости
npm install

# 2. Настройки
cp .env.example .env
#    За Фаза 0 не пипай нищо — стойностите по подразбиране сочат към
#    локалната база от docker-compose.

# 3. База
docker compose up -d postgres

# 4. Схема и роли
npm run prisma:generate
npm run prisma:deploy

# 5. Пускане — два процеса, в два терминала
npm run dev
npm run worker
```

> Работникът е отделен процес нарочно: една генерация държи процеса зает
> 20–60 секунди, а уеб приложението трябва да отговаря веднага. Без пуснат
> работник заявките влизат в опашката и стоят там.

Отвори <http://localhost:3000> и <http://localhost:3000/api/health>.

Здравата проверка връща:

```json
{ "status": "ok", "db": true, "version": "dev" }
```

Ако базата не отговаря, връща `503` и `"db": false`. Така хостингът знае
да не насочва трафик към счупен контейнер.

> **Ако не ползваш `docker compose`,** а вече имаш свой Postgres: създай
> базата и ролите по образец на `docker/postgres/init/01-roles.sql`, после
> пусни `npm run db:setup`. Скриптът взима паролите от връзките в `.env` и
> ги прилага на ролите — един източник на истината.

## Как е защитена базата

Едно приложение, но четири различни роли в базата. Това не е излишно
усложнение — то е причината пробив в потребителската част да не стигне
до парите.

| Роля | Връзка | Може |
|---|---|---|
| `probvai_migrator` | `DATABASE_URL` | Само миграции. Собственик на таблиците. |
| `app_user` | `DATABASE_URL_APP` | Чете и пише **само** своите редове. Няма право да пипа `credits`. |
| `app_system` | `DATABASE_URL_SYSTEM` | Auth.js, Stripe webhook-ове, работници, cron. Не вижда одитния лог. |
| `app_admin` | `DATABASE_URL_ADMIN` | Админ панелът. Единствената роля с достъп до одитния лог. |

Разделянето на редовете става от самата база чрез Row Level Security.
Приложението обявява кой е потребителят в началото на всяка транзакция:

```sql
SELECT set_config('app.current_user_id', $1, TRUE);
```

Ако този ред липсва, политиките не връщат **нито един** ред. Отказът по
подразбиране е правилният отказ.

Заявките от името на потребител минават през `dbAsUser(userId)`, който се
грижи за това автоматично:

```ts
import { dbAsUser } from '@probvai/db';

const db = dbAsUser(session.user.id);
const mine = await db.generation.findMany(); // само неговите, без where
```

Проверката, че наистина работи, е в `packages/db/test/rls.test.ts`.

## Как влиза потребителят

Auth.js v5. Сесиите живеят **в базата**, не в JWT. Разликата има значение:
сесия в базата може да бъде прекратена веднага — при спиране на акаунт или
при изтриване на профил. JWT е валиден, докато не изтече, и никой не може
да го отмени.

Входове: Google · Apple · Facebook · връзка по имейл (magic link).
Включват се само доставчиците, за които има ключове в средата, така че
проектът тръгва и само с magic link.

**Без ключ за Resend в режим на разработка писмото се изписва в конзолата.**
Целият поток с вход работи локално, без домейн и без акаунт. В production
липсващият ключ е грешка — тихо непратено писмо значи потребител, който не
може да влезе.

## Кредити

`packages/core/src/credits.ts` е единственият път до баланса. Четири функции:

```ts
spendCredit(userId, generationId, onSpent?)   // −1, преди викането на доставчика
addCredits(userId, amount, reason, refId?)    // покупка, подарък, корекция
refundCredit(userId, generationId)            // +1 при провалена генерация
getBalance(userId)
```

Всяка започва със `SELECT credits FROM users WHERE id = $1 FOR UPDATE`.
Без това заключване два отворени таба минават проверката едновременно и
харчат два пъти един кредит.

Отгоре има втори пояс — два частични уникални индекса в базата:

| Индекс | Какво прави невъзможно |
|---|---|
| `credit_ledger_one_time_grants` | втори подарък от вид SIGNUP / EMAIL_VERIFY / PHONE_VERIFY |
| `credit_ledger_ref_once` | второ харчене, второ връщане или второ начисляване за същия `ref_id` |

Проверка и запис са две действия и между тях може да се промъкне заявка.
През уникален индекс не се промъква нищо.

### Безплатни кредити

Максимумът е **3 + 1 + 1 = 5**. Рискът гейтва, не намалява:

| Риск | Какво получава |
|---|---|
| 0–39 | 3 при регистрация, +1 при потвърден имейл, +1 при потвърден телефон |
| 40–69 | нищо, докато не потвърди телефон със SMS; след това пълните 5 |
| 70+ | нула — и никога не разбира защо |

Повторна регистрация след изтрит профил също дава нула. Проверката е по
SHA-256 хеш на имейла в `deleted_identities`.

## Генерация

```
POST   /api/generate                  →  { generationId }
GET    /api/generate/{id}             →  състояние, резултат, предложения
DELETE /api/generate/{id}             →  маха проба от гардероба
GET    /api/generate/{id}/stream      →  живо състояние (SSE)
POST   /api/generate/{id}/save        →  свалена е в галерията
POST   /api/generate/{id}/publish     →  в Lookbook или вън от него
PATCH  /api/generate/{id}/category    →  ръчна смяна на стила
POST   /api/extract-garment           →  дреха от линк на магазин
POST   /api/upload                    →  качване на снимка
GET    /api/images/{ключ}             →  пренасочва към подписан адрес

GET    /api/wardrobe                  →  гардеробът, с филтър по категория
GET    /api/lookbook                  →  страница от публичната галерия
POST   /api/lookbook/{id}/like        →  ❤️ обръща състоянието
POST   /api/lookbook/{id}/save        →  ⭐ обръща състоянието
POST   /api/lookbook/{id}/try         →  ✨ взима дрехата за собствена проба
GET    /api/lookbook/{id}/image       →  снимка на публикувана визия

POST   /api/profile                   →  довършва регистрацията
POST   /api/checkout                  →  адрес към Stripe
POST   /api/webhooks/stripe           →  начислява кредитите
```

### Редът на стъпките не се променя

```
1. сесия
2. изчакване между заявките (15 сек)
3. ГЛОБАЛЕН ДНЕВЕН ТАВАН              ← аварийната спирачка
4. дневен лимит на потребителя (50)
5. ТРАНЗАКЦИЯ: FOR UPDATE → леджер → баланс → generations
6. задача в pg-boss
7. връщаме generationId
```

Кредитът се удържа **преди** доставчикът да бъде докоснат. Обърне ли се
редът, два отворени таба правят две снимки срещу един кредит.

### Трите аварийни спирачки

| Спирачка | Стойност | Какво пази |
|---|---|---|
| Глобален дневен таван | `MAX_DAILY_SPEND_USD` | една дупка да не струва €3000 за нощ |
| Дневен лимит на потребител | `MAX_GENERATIONS_PER_USER_PER_DAY` | един разгорещен акаунт |
| Изчакване между заявките | `GENERATION_COOLDOWN_SECONDS` | двоен натиск на бутона |
| Режим на поддръжка | `MAINTENANCE_MODE=1` | спира всичко на секундата |

Себестойността се **запазва при създаването** на генерацията, не при успех.
Иначе сто едновременни заявки виждат нулев разход, минават заедно и после
всичките сто се изпълняват. При провал стойността се нулира.

### Доставчици

| Име | Модел | Заковано | Цена |
|---|---|---|---|
| `fashn_tryon_max` | `tryon-max` | `generation_mode: fast`, `resolution: 1k` | $0.075 |
| `fashn_v16` | `tryon-v1.6` | `mode: performance` | $0.075 |
| `fal_image_apps_v2` | `image-apps-v2/virtual-try-on` | — | $0.040 |

Режимът и резолюцията са закoвани в кода — не са параметри, не се четат от
средата и не се приемат от клиента. При `quality` + `2k` себестойността
надхвърля €0.20 и работим на загуба.

Единствената настройка за потребителя е съотношението на кадъра:
`auto` · `3:4` · `4:5` · `9:16` · `1:1`. Валидира се на сървъра; всичко
извън списъка е отказ **без** харчене на кредит.

### Защита от SSRF

`/api/extract-garment` отваря адрес, подаден от потребител. Проверката на
адреса е при **самото свързване** — подаваме на undici собствена `lookup`
функция, която отказва частните диапазони. Между проверката и връзката няма
прозорец, значи DNS rebinding не минава.

Отгоре: само http/https, ръчно следене на пренасочванията с пълна проверка
на всяка стъпка, таймаут 5 секунди, таван 2 MB.

### Воден знак

Воден знак носят генерациите на потребител, който **никога не е купувал
кредити**. Купи ли веднъж, всичко след това излиза чисто — това е и
обещанието на бутона „Махни водния знак".

## Плащания

```
POST /api/checkout          →  { url } — адрес към Stripe
POST /api/webhooks/stripe   →  единственото място, което начислява кредити
```

Плъзгач от **25 до 200 кредита**, стъпка 5, **€0.20 на кредит**. Минимумът
е 25 кредита, тоест **€5.00**, и това е изписано на екрана за зареждане.

### Три правила, от които излиза всичко останало

1. **Сумата се смята на сървъра.** Клиентът праща само число „колко
   кредита". Пращаше ли цената, всеки щеше да си купи 200 кредита за цент.
2. **Кредити се зареждат само срещу подпис от Stripe.** Не при създаване на
   сесията и не при връщането на човека — връщането е пренасочване в
   браузъра и се пише на ръка в адресната лента.
3. **`checkout.session.completed` не значи „платено".** При отложено
   плащане идва с `payment_status: 'unpaid'`. Гледаме статуса, не събитието.

### Идемпотентност — три пояса

Stripe праща едно и също събитие повече от веднъж. Това не е грешка, а
дизайн.

| Пояс | Какво спира |
|---|---|
| `processed_webhooks` | второ събитие със същия `event.id` |
| `credit_ledger_ref_once` | второ начисляване за същата сесия, дори през друго събитие |
| `SELECT ... FOR UPDATE` | две едновременни доставки на едно събитие |

Върнато плащане отнема кредитите пропорционално. Балансът **не пада под
нула**: ако купеното вече е изхарчено, разликата е наша загуба и се вижда в
леджера. Водният знак се връща, защото `hasEverPurchased` брои СУМАТА на
покупките, не наличието на ред.

## Гардероб, Lookbook и нива

### Категориите се слагат сами

След всяка готова визия `packages/core/src/style.ts` ѝ дава категория —
Бизнес, Стрийт, Лукс, Лято, Елегантно, Сладко, Спорт, Сватба, Парти,
Ежедневно, Среща. Човек може да я смени; тогава тя се заключва и
автоматиката повече не я пипа.

Правилата четат заглавието и адреса на продукта, когато дрехата е дошла
през линк. Няма модел, който гледа снимката — `classifyByVision` е мястото,
където се закача такъв, и до тогава връща `null`.

### Името на магазина

Показва се **само** при генерация от линк (`source = LINK`). При качена
снимка нямаме откъде да знаем от кой магазин е дрехата, а измислено име е
по-лошо от липсващо. Правилото се налага на три места: при записа, при
четенето и в интерфейса.

### Lookbook

Публична галерия и нищо повече. **Няма профили, няма последователи, няма
чат и няма коментари.** Под всяка визия има точно три неща: ❤️ Харесай,
⭐ Запази, ✨ Пробвай този аутфит.

| | |
|---|---|
| Публичен гардероб | изключен по подразбиране, включва се нарочно |
| Публикуване | по ЕДНА визия, с изрично натискане |
| Под 18 години | не публикува, независимо от отметката |
| Подредба | на случаен принцип, стабилна докато се скролва |

Подредбата е `md5(id ‖ семе)`, не `ORDER BY random()`. При второто всяка
следваща страница се пренарежда: една визия излиза три пъти, друга не
излиза изобщо.

Галерията се чете през системната роля, през един файл — `lookbook.ts` —
който избира изрично колоните за показване. Политика „чети всички
публикувани" би отворила и `person_key`, и `cost_usd`: правата в Postgres
са на колона и таблица, не на политика.

### Нива и VIP Closet

Две отделни стълбици, нарочно:

| | Качва се с | Дава |
|---|---|---|
| Newbie Stylist → Fashion Lover → Trend Hunter → Style Expert → Fashion Icon | по една точка на **готова** визия | напредък, който се вижда |
| **VIP Closet** | `VIP_THRESHOLD_EUR` похарчени | HD, значка, предимство на опашката |

Никъде не пише „премиум", „план" или „абонамент". VIP Closet се **отключва**,
не се купува — разликата е между разход и постижение.

Точка се дава за ГОТОВА визия. Провалената връща кредита и не бива да качва
нивото — иначе нивата растат от нашите грешки.

## Правила, които важат за целия код

1. **Нищо специфично за Railway.** Приложението тръгва на всеки Docker хост.
2. **Нула твърдо зашити стойности.** Всяка цена, лимит и праг минава през
   `packages/core/src/env.ts`.
3. **Никакви тайни в браузъра.** Префиксът `NEXT_PUBLIC_` е забранен.
4. **Кредитите се пипат само на едно място** — `packages/core/src/credits.ts`.
   Базата го налага: ролята `app_user` няма `UPDATE` върху колоната `credits`.
